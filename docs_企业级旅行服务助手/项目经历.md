# 企业智行 · Corporate Journey Hub　　AI大模型应用开发工程师　　2026/06 - 2026/08

## 项目背景：

　　针对企业差旅安排分散在邮件、IM、Excel 中，人工规划效率低、差旅合规难管控、行程变更响应慢等问题，设计并开发基于大模型多智能体协作的企业差旅管理平台。系统由三个 FastAPI 微服务（Agent 编排中心、行程规划引擎、实时感知引擎）组成，通过 LangGraph 意图路由实现多 Agent 动态分发，结合 RAG 差旅政策知识库、SSE 流式行程生成、多源实时数据监控与审批自动流转，覆盖企业差旅「行前规划 → 行中保障 → 行后归档」全链路。

## 主要职责：

- 搭建平台整体微服务架构：编排 / 规划 / 感知三层 FastAPI 服务 + shared 公共复用层 + React 19 前端，基于 LangGraph StateGraph 构建意图路由工作流（规划 / 问答 / 管理 / 应急四类意图），存储、鉴权、LLM 管理等平台能力下沉公共层实现零重复代码。
- 设计并开发行程规划 Agent：两阶段生成流程——大模型参数提取（目的地 / 日期 / 人数 / 预算）+ 按规划规则生成多日结构化行程 JSON（含交通、住宿、会议、餐饮、清单与预算），SSE 逐 token 流式输出，支持混元 / DeepSeek / GLM / 小米 MiMo 多模型热切换全链路透传。
- 构建差旅政策 RAG 知识库：实现可插拔 Embedding 三后端（本地 bge-large-zh 私有化 / OpenAI 兼容 API / 关键词降级），失败熔断自动降级；智能问答对政策类问题自动检索政策原文注入回答依据，检索结果保留原文 excerpt 与相似度 score 供大模型引用作答，满足差旅合规可解释性要求。
- 开发实时感知引擎：基于 APScheduler 定时轮询订阅任务（航班动态 / 铁路 12306 车票 / 天气预警 / 路况拥堵 / 景点状态），其中铁路数据源免 Key 查询 12306 余票接口，感知车次停运、无票候补并分级推送；对接多源外部 API 并内置 Mock 降级体系，保障行程变更 60 秒内触达。
- 打通企业化管控链路：行程生成后自动匹配职级差旅政策、检查超标项并发起审批，实现审批门禁闭环（行程待主管审批不可调整，审批通过行程才生效，拒绝则作废），覆盖组织架构、差旅政策、审批流转全流程。
- 设计并实现登录权限与管理员配置中心：账号 Token 认证（24 小时有效期）、管理员 / 员工角色分离（前端导航按角色显隐 + 后端接口双重拦截）、口令加盐哈希存储；管理端支持可用模型列表维护、默认模型切换与 LLM 服务商（接口地址 / 密钥）在线热更新，修改立即生效且密钥脱敏展示。
- 主导系统稳定性与性能治理：定位并修复 async 路由同步执行 LLM 调用阻塞事件循环导致整服务卡死的问题（线程池化）、生成器全局单例并发串单问题（每请求独立实例）、LLM 异常文本污染流式行程 JSON 问题（独立 error 帧协议 + chat_json 保护重试）、JSON 存储非原子写问题（temp + rename 原子写 + 线程锁）；问答首字响应优化至 1.3 秒。
- 完成多服务商模型差异适配：针对推理型模型（小米 MiMo）接入中暴露的流式空 choices 帧解析崩溃、思考过程消耗 max_tokens 预算导致正文为空、JSON 输出格式瑕疵三类问题，在 LLM 管理器协议层统一收敛（帧解析健壮化、token 预算下限、{} 块提取兜底），上层业务零改动。
- 完善安全与数据治理：收窄鉴权后门（dev 万能 key 仅开发环境生效）、补齐行程属主校验防越权访问（IDOR）、修复相对数据路径按服务工作目录解析导致的数据孤岛问题并完成存量数据迁移合并。
- 推进工程化建设：将 1200 行单体路由文件按领域拆分为 7 个 APIRouter 模块，编写六项端到端自动化验证（生成 / 越权 / 阻塞 / 并发 / 政策审批链路 / 流式）与幂等种子数据脚本，全链路接入 Prometheus 指标、结构化 JSON 日志与链路追踪。

## 项目难点：

- 大模型生成多日行程耗时长（数十秒），且早期 async 路由中同步调用 LLM 会阻塞整个事件循环，单请求即可卡死全部服务。通过流式协议改造（逐 token 透传 + 独立错误帧）与线程池化，实现问答首字 1.3 秒、行程生成全程可感知，服务在长耗时请求期间保持健康响应。
- 多用户并发使用时存在一致性问题：全局生成器单例被并发请求互相覆盖模型配置、共享解析结果导致"串单"；JSON 文件存储并发写入易损坏。通过请求级实例隔离与原子写（临时文件 + 原子替换 + 互斥锁）解决，并写入 E2E 并发回归验证。
- 接入新的推理型模型（小米 MiMo）时暴露三类服务商差异：流式响应包含空 choices 帧（解析崩溃）、思考过程消耗 token 预算（正文被截断为空）、JSON 输出带格式瑕疵。通过在 LLM 管理器协议层统一适配（帧解析健壮化 + token 预算下限 + {} 块提取兜底），上层业务代码零改动即完成新模型接入——验证了公共层抽象的价值。
- 企业内无外部数据源 API Key 时需保证系统完整可用与可演示：设计全链路降级体系（LLM 不可用走模板行程、向量检索降级关键词、四类感知数据源降级 Mock），任何依赖缺失下功能链路不断、仅数据降级。
