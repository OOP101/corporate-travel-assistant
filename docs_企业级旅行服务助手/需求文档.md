# 企业智行 — 产品需求文档（PRD）

> 版本：v2.0 ｜ 日期：2026-08-27 ｜ 状态：已定稿（P0 已交付，P1/P2 规划中）
> v2.0 修订说明：业务定位由「个人出行助手」调整为「企业内部行程规划与安排平台」，覆盖员工差旅、客户拜访、会议参展、团队出行等企业内部行程场景。

---

## 一、项目概述

### 1.1 项目名称

**企业智行**（Corporate Journey Hub）

### 1.2 一句话定义

一个面向企业内部的智能行程规划与安排平台，以 LLM 为大脑、以多源实时数据为感知，覆盖「行前规划 → 行中保障 → 行后归档」全链路，让员工一句话生成可执行的差旅行程，让行程安排、实时应变、费用归档从分散的多方沟通中解放出来。

### 1.3 项目背景与痛点

| 痛点 | 现状描述 |
|:---|:---|
| 行程安排分散 | 差旅信息散落在邮件、IM、Excel、口头沟通中，无统一入口，变更无法同步 |
| 规划成本高 | 员工自行查交通、会议衔接、住宿选址，平均一次出差需 1–2 小时做行程 |
| 实时应变难 | 航班延误、天气突变时，员工手忙脚乱改行程，行政/主管被动响应 |
| 预算口径乱 | 行前无预算预估，行后报销口径不一，财务核对成本高 |
| 经验不复用 | 常用差旅线路（固定客户拜访、参展路线）每次重复规划 |
| 政策落地弱 | 差旅政策（舱位/酒店标准/补贴）靠人工记忆和事后审查，合规成本高 |

### 1.4 目标用户与角色

| 角色 | 占比预估 | 核心诉求 |
|:---|:---|:---|
| 出差员工 | 50% | 一句话生成合规行程，行中有人「管」，行后报销材料齐全 |
| 部门主管 | 15% | 掌握团队行程动态，预算可控，异常行程及时知情 |
| 行政/差旅管理 | 20% | 统一安排多人出行（参展/团建），降低逐人沟通成本 |
| 财务 | 10% | 费用预估前置、行后统计口径统一，报销核验有据 |
| IT/信息安全 | 5% | 私有化部署、接口鉴权、数据不出企业边界 |

### 1.5 核心价值主张

```
一句话描述行程需求 → 分钟级生成可执行差旅行程 → 行中实时应变保障 → 行后费用归档报销
```

- **省时**：行程规划从小时级降至分钟级
- **省心**：实时感知 + 主动推送 + 应变重排
- **合规**：行程即预算、费用即口径（P1 差旅政策库）
- **沉淀**：常用线路模板化，组织级经验复用

## 三、功能需求详述

### 3.1 行前规划模块

#### F1.1 智能行程生成（核心，P0 已交付）

**用户故事**：作为出差员工，我希望用一句话描述出行意图，系统自动生成包含交通、住宿、会议、客户拜访、餐饮的完整日程。

**输入**：自然语言描述，例如：
- "9 月 15 号广州飞北京出差，16 号上午拜访国贸客户，下午内部会议，17 号下午返程"
- "下周三部门 5 人去深圳参加三天行业展会，需要提前一天布展，预算人均 6000"
- "安排我下周一到周三去成都分公司做例行巡检，周二晚上和当地团队聚餐"

**生成内容**：
- 按天/时段排列的时间线（含出发时间、交通方式、预计耗时）
- 会议/客户拜访日程（含地点、时长、衔接缓冲）
- 餐饮安排（公务宴请 / 工作餐）
- 住宿区域建议（按会议地点便利度 + 预算匹配）
- 交通方案（城际大交通 + 市内通勤方案）

**输出格式**：结构化行程卡片 + 可导出（Web 工作台查看）

**约束规则**：
- 单日核心活动不超过 4 个，避免行程过密
- 相邻活动地点步行/车程 ≤ 30 分钟
- 午餐/晚餐时段预留 1–1.5 小时
- 商务场景优先保障会议时段不被打扰，预留缓冲
- 多人团队出行自动对齐集合时间与共同日程

---

#### F1.2 出行清单生成（P0 已交付）

**用户故事**：出发前我希望系统根据目的地和行程性质，自动生成一份出行清单。

**生成逻辑**：
- 目的地气候 → 衣物建议
- 行程性质 → 装备建议（参展 → 物料清单；巡检 → 工具设备）
- 企业出行 → 证件与公司材料（工牌、名片、合同、发票抬头信息）
- 可勾选确认 + 自定义增删

---

#### F1.3 预算预估（P0 已交付：行程级费用统计）

**用户故事**：作为员工，我希望行前即拿到费用预估，用于差旅预算申报；作为主管，我希望看到预算与实际对比。

**能力**：
- 按行程项（交通/住宿/餐饮/杂费）预估费用
- 行程详情页展示分类费用汇总
- P1：对接差旅政策标准（职级舱位/酒店上限），超标预警

**优先级**：P0（预估+统计）/ P1（政策对齐）

---

#### F1.4 差旅政策适配（P1 规划）

**用户故事**：作为行政，我希望行程生成时自动遵守公司差旅政策，而非事后审查。

**能力**：
- 差旅政策文档入库（RAG 检索）：舱位标准、酒店上限、补贴标准
- 行程生成时按员工职级/出行城市匹配政策约束
- 超标项生成提示（需额外审批）

---

### 3.2 行中保障模块

#### F2.1 实时行程提醒（P0 已交付）

**用户故事**：出行途中我希望系统在关键时刻主动提醒我，而不是我盯着看。

**提醒类型**：

| 提醒场景 | 触发条件 | 提前量 |
|:---|:---|:---|
| 出发提醒 | 该出发去机场/车站了 | 按实时路况计算 + 30 分钟缓冲 |
| 登机/检票提醒 | 航班/列车开始登机检票 | 提前 30 分钟 |
| 行程切换提醒 | 当前活动即将结束，下一站该出发 | 提前 15 分钟 |
| 天气突变提醒 | 目的地突降暴雨/大风/极端天气 | 实时 |
| 航班延误提醒 | 航班状态变更 | 实时 |
| 场馆/景点闭馆提醒 | 当日计划场所临时关闭 | 检测到即推送 |

**推送渠道**：Web 工作台通知（P0）/ 企业 IM 机器人（P1 规划）

---

#### F2.2 智能问答助手（P0 已交付）

**用户故事**：行中遇到问题随时问，比如"下一站怎么走""明天几点出发""附近哪里适合宴请客户"。

**能力范围**：
- 基于行程上下文的问答（"明天几点出发""会议地点在哪"）
- 交通/地点/流程类通用问答
- 多轮对话 + 上下文记忆

---

#### F2.3 实时应变与行程重构（P0 已交付）

**用户故事**：航班延误了 / 客户临时改期了，系统主动帮我调整后续行程。

**应变策略**：
- 航班延误 → 自动延后后续酒店、宴请安排，提示是否需改签
- 场馆关闭/客户改期 → 重排当日时间线，推荐替代方案
- 恶劣天气 → 将户外活动调整为室内活动
- 用户主动改行程 → 增量重排受影响的后续行程，保持整体连贯

---

#### F2.4 应急协助（P1 规划）

**能力**：
- 证件/设备丢失应对指引
- 就近医院/药店导航
- 紧急联系人（直属主管/行政）通知

---

### 3.3 实时感知模块

#### F3.1 多源数据接入（P0 已交付：航班/天气/路况）

| 数据类型 | 数据源（候选） | 更新频率 |
|:---|:---|:---|
| 航班动态 | 航旅纵横 / Flightradar24 API | 5 分钟 |
| 天气预报 | 和风天气 / OpenWeather API | 1 小时 |
| 实时路况 | 高德 / 百度地图 API | 5 分钟 |
| 场馆状态 | 官方公告抓取 | 30 分钟 |

无 Key 环境自动降级为 Mock 数据源，保证演示完整。

---

#### F3.2 主动感知引擎（P0 已交付）

**机制**：
- 订阅式监控：对当前行程涉及的所有要素（航班号、目的地天气区域）建立监控订阅
- 规则引擎：「异常事件 → 影响判断 → 应对动作」规则链
- 静默去噪：非关键变更不打扰（如航班延误 < 15 分钟静默记录不推送）

---

### 3.4 行后归档模块

#### F4.1 行程总结（P0 已交付）

**内容**：
- 行程概览（天数、城市、总花费）
- 每日回顾（实际执行的活动、路线）
- 偏差分析（计划 vs 实际：哪些取消、哪些临时加）

---

#### F4.2 费用统计与报销材料（P0 已交付：统计；P2 规划：导出）

**能力**：
- 分类费用汇总（交通/住宿/餐饮/门票/杂费），对齐报销口径
- P2：导出报销明细（Excel / 对接报销系统 API）

---

#### F4.3 行程模板复用（P0 已交付）

**用户故事**：固定客户拜访线路、例行巡检，希望一次安排，多次复用。

**能力**：
- 一键保存当前行程为模板
- 模板标签化（城市/天数/场景/季节）
- 生成新行程时优先匹配历史模板微调

---

### 3.5 企业管理层模块（P1/P2 规划）

| 功能 | 说明 | 优先级 |
|:---|:---|:---|
| 组织与人员管理 | 部门/员工/职级档案，作为政策匹配与权限基础 | P1 |
| 差旅审批流 | 行程生成后发起审批，主管审批通过后生效 | P1 |
| 管理报表 | 部门差旅量/费用/异常事件统计看板 | P2 |
| 企业 SSO | OIDC 对接企业身份系统 | P2 |

## 四、非功能需求

### 4.1 性能需求

| 指标 | 目标值 |
|:---|:---|
| 行程生成首字延迟 | ≤ 2 秒（SSE 流式输出）|
| 行程生成完整耗时 | ≤ 30 秒（3 天行程）|
| 实时提醒推送延迟 | 异常事件检测后 ≤ 60 秒 |
| 智能问答响应延迟 | ≤ 3 秒首字 |
| 并发用户支持 | 初期 ≥ 500 并发会话 |

### 4.2 可用性需求

| 指标 | 目标值 |
|:---|:---|
| 服务可用性 | ≥ 99.5% |
| LLM 降级策略 | LLM 不可用时退化为规则模板模式，保证基础可用 |
| 数据源容错 | 单一数据源故障不影响核心流程，自动切换备用源 |
| 离线能力 | 已生成行程离线可查看 |

### 4.3 安全与合规

| 维度 | 要求 |
|:---|:---|
| 企业数据 | 行程数据属企业内部数据，支持私有化部署，数据不出企业边界 |
| 员工信息 | 姓名/证件号脱敏存储，仅展示必要字段 |
| API 鉴权 | 全部接口需 API Key / Token 鉴权，按用户隔离会话 |
| 数据留存 | 行程数据默认保留 2 年，管理员可配置清理策略 |
| 合规 | 遵守《个人信息保护法》《数据出境安全评估办法》 |

### 4.4 可观测性

| 维度 | 要求 |
|:---|:---|
| 指标监控 | Prometheus：请求量/延迟/错误率/LLM Token 消耗/数据源健康度 |
| 链路追踪 | 每次行程生成/问答全链路 Trace |
| 结构化日志 | JSON 格式，含 trace_id / session_id / user_id |
| 告警 | 数据源连续失败、LLM 错误率超阈值、提醒推送失败率 > 5% 时告警 |

## 五、技术架构

### 5.1 架构分层

```
┌─────────────────────────────────────────────────────┐
│                  用户交互层                          │
│         Web 工作台 (React) · REST/SSE API            │
├─────────────────────────────────────────────────────┤
│                  Agent 编排层                        │
│   LangGraph 多 Agent 工作流（意图路由 → 规划 → 应变）  │
├──────────────┬──────────────┬───────────────────────┤
│  规划 Agent   │  问答 Agent   │    应变 Agent         │
│  行程生成     │  行程问答     │    实时监控+重排       │
│  清单/预估    │  多轮对话     │    应急指引           │
├──────────────┴──────────────┴───────────────────────┤
│                  能力服务层                          │
│     LLM 服务 · 政策 RAG 检索 (P1) · 数据源适配        │
├─────────────────────────────────────────────────────┤
│                  数据感知层                          │
│     航班监控 · 天气监控 · 路况监控 · 场馆状态         │
├─────────────────────────────────────────────────────┤
│                  数据存储层                          │
│     行程 JSON 存储 (data/) · 会话存储 · 模板库        │
└─────────────────────────────────────────────────────┘
```

### 5.2 核心技术选型

| 层级 | 技术选型 | 说明 |
|:---|:---|:---|
| 后端框架 | FastAPI + Uvicorn | 异步 REST + SSE 流式 |
| AI 编排 | LangGraph | 有状态多 Agent 工作流 |
| LLM | DeepSeek / Qwen / GLM | 多服务商注册表，可切换 |
| 前端 | React 19 + Vite + Tailwind CSS 4 | Web 工作台 |
| 定时调度 | APScheduler | 感知引擎周期检查 |
| HTTP 客户端 | requests | 连接池 + 自动重试 |
| 可观测性 | Prometheus + 结构化日志 | 指标 + 追踪 |
| 容器化 | Docker + Docker Compose | 部署编排 |

### 5.3 微服务拆分

| 服务 | 代号 | 职责 | 端口 |
|:---|:---|:---|:---|
| 行智 | journey-hub | Agent 编排中心：意图路由、会话管理、SSE 对话 | 8001 |
| 策程 | planner-core | 行程规划引擎：生成、存储、清单、归档、重排 | 8002 |
| 感知 | sense-engine | 实时感知引擎：多源监控、异常检测、提醒 | 8003 |

### 5.4 Agent 工作流设计

```
员工输入
   │
   ▼
意图路由 (route)
   ├── 规划意图 ──→ 规划 Agent ──→ 行程生成 ──→ 输出行程卡片
   ├── 问答意图 ──→ 问答 Agent ──→ 上下文检索 + LLM ──→ 流式回答
   ├── 应变意图 ──→ 应变 Agent ──→ 影响分析 + 重排 ──→ 更新行程
   └── 管理意图 ──→ 管理 Agent ──→ 查看/编辑/归档 ──→ 返回结果
```

### 5.5 实时感知引擎设计

```
定时调度 (APScheduler)
   │
   ├── 航班监控任务 ──→ 调用航班API ──→ 状态变更检测
   ├── 天气监控任务 ──→ 调用天气API ──→ 预警阈值判断
   ├── 路况监控任务 ──→ 调用地图API ──→ 拥堵/封路检测
   └── 场馆状态任务 ──→ 抓取官方公告 ──→ 闭馆/开放变更
                              │
                              ▼
                    影响分析 (LLM/规则)
                    "这个事件影响谁的哪段行程？"
                              │
                              ▼
                    应对决策 (规则链)
                    "静默记录 / 推送提醒 / 触发重排"
                              │
                              ▼
                    推送引擎 ──→ 员工/管理员
```

## 六、数据模型（核心）

### 6.1 核心实体

```
User (员工)                        [P1]
 ├── department / title             部门/职级（政策匹配）
 ├── trips                 行程列表 (1:N)
 │    ├── trip_days        每日安排 (1:N)
 │    │    └── activities  时段活动 (1:N)
 │    ├── alerts           提醒队列 (1:N)
 │    └── expenses         费用记录 (1:N)
 └── templates             行程模板 (1:N)
```

## 七、API 设计（核心接口）

### 7.1 行程规划（planner-core :8002）

| 方法 | 路径 | 说明 |
|:---|:---|:---|
| POST | `/trips/generate` | 流式生成行程（SSE） |
| GET | `/trips` | 行程列表 |
| GET | `/trips/{trip_id}` | 行程详情 |
| PUT | `/trips/{trip_id}` | 编辑行程 |
| DELETE | `/trips/{trip_id}` | 删除行程 |
| POST | `/trips/{trip_id}/reroute` | 应变重排 |
| GET | `/trips/{trip_id}/checklist` | 出行清单 |
| POST | `/trips/{trip_id}/summary` | 行程总结 |
| GET | `/trips/{trip_id}/expenses` | 费用统计 |

### 7.2 智能问答（journey-hub :8001）

| 方法 | 路径 | 说明 |
|:---|:---|:---|
| POST | `/agent/chat` | 多轮对话问答 |
| POST | `/agent/chat/stream` | SSE 流式对话 |
| GET | `/agent/sessions` | 活跃会话列表 |

### 7.3 实时感知（sense-engine :8003）

| 方法 | 路径 | 说明 |
|:---|:---|:---|
| GET | `/trips/{trip_id}/alerts` | 当前行程关联的实时提醒 |
| POST | `/monitor/subscribe` | 为行程订阅监控（航班/天气/路况） |
| GET | `/monitor/status` | 监控任务运行状态 |
| DELETE | `/monitor/{trip_id}` | 取消订阅 |
| POST | `/monitor/check` | 手动触发检查 |

> 所有接口需 `X-API-Key` 请求头鉴权。

## 八、用户交互流程

### 8.1 行前规划主流程

```
员工输入一句话差旅需求
        │
        ▼
  意图理解 + 信息抽取
  (目的地/日期/人数/预算/场景)
        │
        ▼
  缺失信息追问 ──── 关键信息齐全 ────┐
        │                            │
        ▼                            ▼
  多源数据查询               规划 Agent 编排
  (天气/交通/场馆)          (LangGraph 工作流)
        │                            │
        └──────────┬─────────────────┘
                   ▼
          生成行程草稿 (SSE 流式)
                   │
                   ▼
          员工预览 + 可编辑调整
                   │
                   ▼
          确认保存（自动订阅监控）
```

### 8.2 行中保障主流程

```
行程开始 (到达出发日)
        │
        ▼
  激活实时感知引擎
  (订阅航班/天气/路况)
        │
        ├── 定时检查 ──→ 无异常 ──→ 静默
        │
        ├── 检测异常 ──→ 影响分析 ──→ 推送提醒
        │                              │
        │                              ├── 仅提醒
        │                              └── 建议重排 ──→ 员工确认 ──→ 更新行程
        │
        └── 员工主动提问 ──→ 问答 Agent ──→ 流式回答
```

## 十、验收标准

### 10.1 功能验收

| # | 验收项 | 通过标准 |
|:---|:---|:---|
| 1 | 一句话生成行程 | 输入自然语言差旅需求，30 秒内输出结构化多日行程，含交通/会议/餐饮 |
| 2 | 行程合理性 | 相邻活动通勤 ≤ 30 分钟，会议时段预留缓冲，预留用餐时间 |
| 3 | 商务场景生效 | 指定拜访/会议后，行程保障 meeting 时段优先 |
| 4 | 智能问答 | 行中提问 3 秒内首字响应，回答基于行程上下文 |
| 5 | 实时提醒 | 航班延误/天气突变检测后 60 秒内推送提醒 |
| 6 | 应变重排 | 场馆关闭/客户改期后，推荐替代方案并重排当日时间线 |
| 7 | 费用统计 | 行程详情页展示分类费用汇总，口径对齐报销分类 |
| 8 | 降级兜底 | LLM 不可用时退化为规则模板，基础行程仍可生成 |

### 10.2 非功能验收

| # | 验收项 | 通过标准 |
|:---|:---|:---|
| 1 | 性能 | 行程生成 ≤ 30 秒，问答首字 ≤ 3 秒，500 并发不降级 |
| 2 | 可用性 | 服务可用性 ≥ 99.5%，单数据源故障不中断核心流程 |
| 3 | 可观测 | Prometheus 指标 + 全链路 Trace 可查，关键告警生效 |
| 4 | 安全 | 全接口鉴权，员工信息脱敏，支持私有化部署 |

## 十一、风险与对策

| 风险 | 影响 | 概率 | 对策 |
|:---|:---|:---|:---|
| 外部数据源 API 不稳定或收费高 | 实时感知能力受限 | 高 | 多源冗余 + Mock 兜底 + 降级为离线规则 |
| LLM 行程生成质量不稳定 | 用户体验差 | 中 | Prompt 工程迭代 + 结构化输出约束 + 人工评测集 |
| 企业数据安全顾虑 | 私有化诉求阻碍推广 | 中 | 支持私有化部署，数据不出企业边界 |
| 差旅政策多样（分子公司不同） | 政策库维护成本高 | 中 | 政策模板化 + 分级配置（P1） |
| 审批流与现有 OA 系统冲突 | 推广阻力 | 中 | P1 提供标准审批流 + API 对接已有 OA |
