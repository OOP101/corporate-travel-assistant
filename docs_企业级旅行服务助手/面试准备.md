## 第一部分 · 技术详解

### 1. 整体架构：三层微服务 + 公共复用层

```
journey-hub (8001, Agent 编排)  ←  用户对话入口，LangGraph 意图路由
   ├── planner-core (8002, 行程规划)  ←  行程生成/CRUD/政策/审批
   └── sense-engine (8003, 实时感知)  ←  航班/天气/路况/景点监控
shared/  ←  LLM 管理器、配置、鉴权、存储基类、指标、日志、HTTP 客户端
frontend/  ←  React 19 + Vite + Tailwind，7 个页面
```

**为什么拆三个服务**：三者职责与生命周期不同——编排服务面向用户（对话态、会话记忆）、规划服务是核心业务（CRUD + LLM 生成）、感知服务是定时任务型（轮询 + 推送）。拆开后各自独立扩缩容（感知服务 CPU 密集可多副本），且服务间用 REST/SSE 标准协议，未来可独立替换实现。

**shared 层解决什么**：三个服务原本会各自实现一遍 LLM 调用、API Key 鉴权、JSON 存储。抽成公共层后（`LLMManager`、`APIKeyAuth`、`BaseJsonStore`、`ServiceClient`、`settings`），修改一处全平台生效——例如批次 1 给 `chat_stream` 统一加 UTF-8 charset 修复和错误抛出，三个服务同时受益。

### 2. LangGraph 意图路由（StateGraph）

- **是什么**：LangGraph 是 LangChain 团队的状态图编排框架，把 Agent 流程建模为「节点（函数）+ 边（流转条件）」的状态机，天然支持条件分支、循环和检查点。
- **项目中的图**：`route → (plan → preflight → respond) | chat → respond | manage → respond | emergency → respond`，意图分类用关键词规则引擎（正则 + 优先级词表：应急 > 管理 > 规划 > 问答兜底），毫秒级完成、零成本。
- **为什么规则不用 LLM 分类**：意图集合小且关键词区分度高（"规划/行程" vs "删除/查看" vs "应急/报警"），规则分类零延迟零成本，还避免了 LLM 分类本身的不稳定。代码中预留了替换为轻量 LLM few-shot 分类的口子。
- **会话记忆**：`MemorySaver` checkpointer + 自研 `SessionManager`（每会话保留 20 条历史），`thread_id = session_id` 隔离多用户上下文。

### 3. LLM 多模型接入与流式（LLMManager）

- **统一注册表模式**：`register(name, api_key, base_url, model, ...)` 注册 OpenAI 兼容服务商（腾讯 TokenHub：混元 / DeepSeek / GLM），全链路透传 `model` 参数实现前端热切换，切换无需改代码。
- **两阶段行程生成**：阶段一 `chat_json`（`response_format=json_object`，temperature=0.1）提取结构化参数；阶段二 `chat_stream`（temperature=0.4, max_tokens=8192）按系统提示词里的规划规则（单日 ≤4 景点、通勤 ≤30 分钟、正餐时段等）生成行程 JSON。
- **流式协议**：后端 SSE 帧协议 `route / intent / chunk / respond / error / done`。三条硬规则：①错误必须走独立 error 帧，绝不混入正文（会污染下游 JSON 解析）；②SSE 响应必须带 `; charset=utf-8`（否则 RFC 2616 回退 ISO-8859-1 产生中文乱码）；③`respond` 整帧保留以兼容前端整体替换契约。
- **健壮性**：`chat_json` 失败重试 1 次后抛 `LLMError`；流式网络异常抛 `LLMError` 由上层降级；无 API Key 时 `is_available()=False` 走模板行程，保证无 Key 完整可演示。

### 4. RAG 差旅政策知识库

- **链路**：政策文档（标题+正文）入库 → Embedding 向量化 → 检索时查询向量化 → 余弦相似度 Top-K → 结果携带原文 excerpt 与 score 给 LLM 引用作答。
- **可插拔三后端**（`EMBEDDING_PROVIDER` 切换）：`local`（sentence-transformers 加载 BAAI/bge-large-zh-v1.5，1024 维，数据不出企业）/ `api`（OpenAI 兼容 `/embeddings` 接口）/ `none`（关键词检索兜底）。auto 模式探测可用性自动选择，探测失败熔断（不再重复请求）。
- **为什么选 bge**：中文语义表征优于 OpenAI ada（国内延迟高）和 M3E（中文长尾差）；bge-large 1024 维在检索精度和存储成本间平衡。
- **降级路径**：向量不可用时自动降级为关键词检索（`search_by_keyword`），接口返回 `mode` 字段标明本次走的是 vector 还是 keyword，保证功能永远可用。
- **增量索引**：`index_missing_embeddings` 只对缺向量的文档增量补齐，查询时顺带补索引，无需人工重建。

### 5. 审批与政策管控闭环（PRD 3.5）

- **状态机**：行程生成 → 命中政策（`requires_approval` 或预算 ≥ 阈值）→ 自动创建审批单（审批人 = 员工直属主管）→ 行程置 `pending_approval` → 主管通过置 `planned` 生效 / 拒绝置 `cancelled` 作废。
- **门禁点**：`pending_approval` 状态的行程禁止应变重排（409）。
- **员工解析**：会话 ID 恰为员工 ID 时按职级匹配政策（精确职级 > 通用政策 > 城市等级匹配）；链路任一环节失败只告警不阻断行程生成（增强链路与主链路解耦）。
- **违规检查**：规则引擎逐活动核对（住宿超 hotel_limit / 餐饮超 meal_limit），违规项随审批单附带给审批人参考。

### 6. 实时感知引擎（sense-engine）

- **订阅制 + 定时轮询**：APScheduler 每 5 分钟跑一轮 `check_all`，只检查已订阅的行程（绑定航班号 / 目的地 / 景点列表），不做全库扫描。
- **四类数据源统一抽象**：`BaseSource.check(subscription) → SourceResult`，航班 / 天气（和风）/ 路况（高德）/ 景点各自实现真实 API 与 `_fetch_mock`，无 Key 自动走 Mock——降级在数据源内部完成，引擎无感知。
- **异常分级**：critical（航班取消）/ warning（延误）/ info（提示），生成 Alert 挂到行程下推送。

### 7. 工程化与可观测性

- **FastAPI + Pydantic**：请求模型校验（字段白名单、Optional 修复 422）、`APIRouter` 按领域拆分（trips/org/policy/policy_docs/approvals 等 7 个模块，主入口从 1200 行减到 140 行装配层）。
- **可观测**：Prometheus 指标（token 用量、节点耗时、工具调用计数、行程生成时长、活跃会话）+ 结构化 JSON 日志（双格式）+ 自研 TraceContext span。
- **鉴权中间件**：`X-API-Key` 头 + workspace 注入 `request.state`；dev 万能 key 仅 `APP_ENV != production` 生效。
- **测试**：62 例 pytest——shared 层（鉴权/存储/LLM/HTTP 客户端）、reroute 算法纯函数、FastAPI TestClient API 集成（临时目录隔离）、六项 E2E（真实 LLM 全链路）。

### 8. 前端（React 19 + Vite 8 + Tailwind 4）

- 组件分层（Atoms/Molecules）+ 7 页面 `React.lazy` 代码分割（每页独立 chunk 4.5~14.5KB）。
- `api/client.js` 统一封装 fetch 错误处理与 SSE 流解析（`data:` 帧逐行解析、`[DONE]` 终止、AbortController 中断）。
- ChatPage 对 `chunk` 帧增量渲染、`respond` 帧整体替换（兼容契约）、`intent` 帧显示意图徽标。

## 第二部分 · 面试问答

### A. 架构与 LangGraph

**Q1：为什么用 LangGraph 而不是直接函数调用或者 AutoGen？**

答：行程管家的流程是多分支状态机——一句话进来先判意图，规划意图还要经过"前置校验（信息不全就追问）→ 调规划工具 → 组织回复"的链路，且未来会加循环（生成质量不达标重新规划）。LangGraph 的 StateGraph 把这种"节点 + 条件边"建模得很自然，自带 checkpointer 做会话检查点，比手写 if-else 可维护，比 AutoGen 的对话式协作更可控——我们的场景需要确定性路由，不需要多个 LLM 自由对话。选型时也考虑过直接函数调用，但图结构让新增意图（比如后来加的 emergency）只是加一个节点 + 一条条件边，扩展成本低。

**Q2：意图分类为什么用规则不用大模型？**

答：实测我们的四类意图（规划/问答/管理/应急）关键词区分度很高——"规划/去/玩" vs "删除/查看/改名" vs "应急/报警/丢失"，规则分类毫秒级、零成本、结果确定。LLM 分类有两个问题：一是本身要 1-2 秒延迟，二是分类结果不稳定可能误路由。当然规则有边界情况（比如"去日本旅游需要什么签证"含"去"会被误判为规划），我们知道这个 trade-off，代码里留了替换为轻量 LLM few-shot 分类的口子，如果实际运营中误分类率高再升级。这个"先简单后复杂"的取舍我认为比一开始就上 LLM 分类更工程化。

**Q3：为什么拆三个微服务？单体不行吗？**

答：演示规模下单体确实够，但三者的扩缩容特征不同：感知服务是定时轮询型（CPU/网络密集、无用户态）、规划服务是 LLM 调用型（长耗时、需要多副本）、编排服务是有状态会话型（内存里挂着会话）。拆开后可以独立扩容规划服务副本而不用动会话层。另一个收益是故障隔离：感知服务的外部 API 挂掉不会影响对话主链路。代价是服务间调用的复杂性，所以我们把协议收敛为两种——REST（同步查询）和 SSE（流式生成），并用 shared 层的 ServiceClient 统一了重试和鉴权。

### B. 流式与性能

**Q4：SSE 和 WebSocket 怎么选的？为什么？**

答：我们的场景是纯服务端单向推送（生成进度、行程片段），客户端不需要在生成过程中往回发消息，SSE 够用且更简单：基于 HTTP 无需协议升级、过网关/代理天然兼容、断线语义清晰。WebSocket 的双向能力和心跳管理在这个场景是多余的复杂度。前端用 fetch + ReadableStream 手动解析 `data:` 帧实现，AbortController 支持用户中途取消。

**Q5：伪流式和真流式的区别？你们怎么发现和解决伪流式的？**

答：伪流式是后端把结果完整算完再一次性吐给前端，前端看起来像流式但首字延迟等于总耗时。我们最初 journey-hub 的 `/agent/chat/stream` 就是伪流式——它等 LangGraph 全图跑完才吐三帧。改造分两层：chat 意图让 LLM 层直接 `chat_stream` 逐 token 透传；plan 意图因为行程摘要要等结构化 JSON 生成完才能格式化，采用"即时状态帧（0.1 秒到达）+ 生成完成后分段产出摘要 + 政策/审批结果渐进补全"的策略。改造后问答首字 1.3 秒、规划请求首帧 0.1 秒。

**Q6：async 路由阻塞事件循环这个问题，原理和修复讲一下。**

答：FastAPI 的 `async def` 路由跑在事件循环上，如果在里面调用同步阻塞函数（requests 的 LLM 调用，单次可达数十秒），事件循环被独占，期间所有请求包括 `/health` 都无响应——等于单请求把整个服务打死。我们线上表现就是：一个人在生成行程，其他所有人的健康检查都超时。修复方案做了最小化选择：把该路由改成普通 `def`，FastAPI 自动把它丢进线程池执行，一行改动解决。没有全面切 httpx 异步化，因为那要改造所有下游调用和并发模型，收益/成本比不划算——线程池的并发上限（默认 40）对这个场景绰绰有余。

**Q7：并发串单问题是怎么发现和修复的？**

答：代码审计时发现 `/trips/generate` 路由直接改写全局单例生成器的 `model` 字段，且依赖生成器实例上的 `_last_trip` 传递解析结果。两个并发请求时：A 改了 model，B 立刻覆盖；A 的流先结束读 `_last_trip`，拿到的是 B 的行程——用户 A 会收到用户 B 的行程数据。修复是每次请求创建独立生成器实例（构造时传入 model），实例状态天然隔离。修复后写了并发 E2E 回归：两个并发生成不同目的地（深圳/成都）的行程，断言各自的 destination 和归属都正确。

**Q8：问答首字 1.3 秒是怎么做到的？**

答：链路上每一段都压过：意图分类用规则（0ms）；LLM 流式接口直接透传，首 token 取决于服务商（混元实测约 1 秒出首 token）；SSE 帧不缓冲（响应头加 `X-Accel-Buffering: no` 防 nginx 缓冲）。规划场景因为要等完整 JSON 无法逐 token 展示，改用 0.1 秒即发的状态帧消除等待感。E2E 里对首帧时间有断言（阈值 3 秒），防止回归。

### C. RAG 与 LLM 应用

**Q9：RAG 检索结果为什么要带原文 excerpt 和相似度？**

答：差旅政策是强合规场景，模型不能给无依据的答案。我们把检索命中的原文片段（excerpt）和余弦相似度（score）一起返回，LLM 的回答必须基于 excerpt 生成，用户可以核对原文出处。这解决两个问题：一是幻觉——模型只能引用检索到的政策原文；二是可解释性——员工质疑"为什么说我超标"时能出示依据。接口还返回 `mode` 字段标明这次走的是向量检索还是关键词降级，方便排查检索质量问题。

**Q10：Embedding 为什么选 bge-large-zh？三后端可插拔怎么设计的？**

答：选型时对比了三类：OpenAI ada（效果可以但国内延迟高、数据出企业）、M3E（中文长尾词效果差）、BAAI bge 系列（中文效果最好的开源系列之一）。选 bge-large-zh-v1.5，1024 维，本地部署数据不出企业，符合私有化要求。三后端设计：`local`（sentence-transformers 本地推理）、`api`（OpenAI 兼容 /embeddings 接口，不用装 torch）、`none`（纯关键词），通过环境变量一键切换，auto 模式自动探测可用性。关键工程细节是失败熔断——探测失败后标记不可用，不会每次查询都去撞超时，这防止了降级路径本身变成性能黑洞。

**Q11：LLM 输出的 JSON 解析失败怎么处理？**

答：三层防御。第一层预防：`response_format=json_object` 强制 JSON 输出 + prompt 里"只输出 JSON 不要解释"。第二层容错解析：剥 markdown 代码块围栏、正则提取第一个 `{...}` 块。第三层兜底：`chat_json` 封装了重试——网络异常或解析失败自动重试一次（间隔 1 秒），仍失败抛 `LLMError`，上层捕获后降级到规则模板行程。另外有个隐蔽问题是我们真实踩过的：流式路径下 LLM 调用失败时错误文本曾被当作正文 chunk 返回，混进行程 JSON 导致下游解析必失败且难排查——修复为错误必须走独立 error 帧，并写了回归测试锁定这个行为。

**Q12：多模型热切换怎么实现的？**

答：LLMManager 是统一注册表，注册时绑定服务商的 api_key/base_url/默认模型，每次调用可显式传 `model` 参数覆盖默认值。前端模型选择器选"混元 Pro / DeepSeek / GLM"后，`model` 参数从请求层一路透传到最终 LLM 调用（journey-hub → planner-core → LLMManager），因为所有服务商都是 OpenAI 兼容接口，切换只是换字符串，不需要适配层。新增服务商也只需 register 一行。

### D. 数据与一致性

**Q13：JSON 文件存储为什么不换数据库？并发写怎么保证安全？**

答：演示阶段的数据规模（几十条行程、单实例部署）下，JSON 文件 + 内存缓存是最简单的方案，零运维。但我们修掉了它的两个真问题：一是非原子写——直接 `open(path,"w")` 覆盖，进程崩溃在写入中途文件就损坏了，改成临时文件 + `os.replace` 原子替换（Windows/Linux 语义都保证原子性）；二是无锁——save/update/delete 加了线程锁保护内存 dict 和落盘的一致性。边界也讲清楚：多 worker 或多实例部署时各进程内存副本独立，这个方案就不行了，需要换 SQLite 或 PG——这是有意识的 trade-off，升级路径已经留好（BaseJsonStore 是所有 Store 的基类，换存储只动一个类）。测试里用 5 线程 × 10 次写锁定了并发安全。

**Q14：数据孤岛问题是怎么回事？**

答：一个非常隐蔽的配置 bug：`.env` 里数据目录是相对路径 `./data/trips`，而三个服务是以各自目录为工作目录启动的，所以 planner 的数据实际写到了 `services/planner-core/data/`，跟项目根的 `data/` 形成两座孤岛——测试、种子脚本、服务三方看到的数据不一致，而且没人发现，因为各自都能正常读写。修复分两层：settings 层加 `_anchor_data_path` 把相对数据路径统一锚定到项目根（根治）；存量数据逐文件校验一致性后迁移合并。这个案例让我对"相对路径 + 非预期 cwd"这个经典坑有了实战体感。

**Q15：IDOR 越权是怎么防的？为什么用 404 而不是 403？**

答：原实现 `GET /trips/{trip_id}` 只按 ID 查库，知道任何 trip_id 就能读写别人的行程。修复：所有行程读写接口加属主校验——调用方声明了身份（session_id）且与行程 `user_id` 不符时拒绝。用 404 而不是 403 是防止资源存在性探测：403 等于告诉攻击者"这个 ID 存在，只是你没权限"。兼容性上做了渐进：未声明身份的调用暂时放行（现有前端不传身份参数），P2 接入企业 SSO 后改为强制校验。这是有意识的阶段性 trade-off，文档里明确记录了升级点。

### E. 工程与协作

**Q16：1200 行的 main.py 是怎么拆的？为什么先拆再开发新功能？**

答：planner-core 的入口文件堆了 9 个领域约 40 个路由加全部 Pydantic 模型。拆法是标准 APIRouter 按领域分文件（trips/组织/政策/政策文档/审批等 7 个），共享的服务实例收到独立的 deps.py（避免 router 和 main 循环导入），main.py 只剩 lifespan 初始化和路由挂载约 140 行。之所以在"行程生成接审批"之前先拆：新功能要往里加约 100 行，往 1200 行的文件里继续堆是负资产。拆分纪律是纯搬家不改行为，拆完跑全量回归（31 条 API 路径逐个验证）再开发新功能。顺带发现并修了一个存量 bug：`/policies/match` 定义在 `/policies/{policy_id}` 之后被路径参数路由吞掉了，一直没人调通过。

**Q17：测试策略是怎样的？62 个测试怎么分布的？**

答：三层。单元测试覆盖 shared 层地基（鉴权后门的环境收窄、存储原子写与并发、LLM 的 JSON 重试与流式错误协议、HTTP 客户端的 SSE 解析）和纯函数算法（行程重排的前移/顺延/重排）；集成测试用 FastAPI TestClient 打真实路由（临时目录隔离数据、LLM 走演示降级），覆盖生成全生命周期、越权、路由可达性；E2E 用真实 LLM 跑六项关键链路（生成、越权、阻塞、并发、政策审批、流式首帧）作为发布前验收。一个具体教训：测试暴露了审批单漏写 status 字段的 bug——审批人列表按 pending 过滤根本看不到新审批单，没有集成测试这个链路断在那里都不会被发现。

**Q18：可观测性做了什么？排障时怎么用？**

答：三个层次。指标：Prometheus 暴露 LLM token 用量、LangGraph 节点耗时、工具调用计数、行程生成时长分布、活跃会话数。日志：结构化 JSON（LOG_JSON 切换），关键字节点带 session_id 方便串联单次会话全链路。追踪：自研轻量 TraceContext span 记录意图路由、工具执行的耗时与结果。实际排障案例：行程总结打不开，先看后端日志确认接口 200 且 4 秒返回，排除服务端后转向前端，发现是 React 渲染对象类型崩溃——可观测性的价值就是把问题空间快速二分。

**Q19：审批门禁的状态机怎么设计的？有没有考虑并发审批？**

答：行程状态 pending_approval → planned（通过）/ cancelled（拒绝），非 pending 状态的审批操作返回 400 防重复处理；待审批行程禁止重排（409）实现门禁。并发审批的防护点是状态前置检查（approve/reject 前校验仍是 pending），当前单实例 + 线程锁下没有竞态窗口；严格说多实例部署需要乐观锁或数据库行锁，这在换存储的升级路径里。实现中修过一个真 bug：审批单创建漏写 status 字段，导致按 pending 过滤的审批人列表看不到新单——整个自动审批链路实际是断的，是端到端验证暴露的。

**Q20：无 API Key 也能完整演示，这个降级体系怎么设计的？**

答：核心原则是"降级在数据源内部完成，上层无感知"。每个依赖都有兜底：LLM 不可用走模板行程生成（基于关键词猜目的地和天数）；向量检索不可用降级关键词检索；航班/天气/路况/景点四类外部 API 各自实现 `_fetch_mock`。上层代码完全不知道当前是真实还是降级模式，接口行为一致。这样设计的好处：一是销售/演示场景零配置跑通全流程；二是开发时外部 API 挂了不影响联调；三是降级路径本身被测试覆盖，不是摆设。

**Q21：这个项目如果重做一次，你会改什么？**

答：三点。一是存储会直接上 SQLite：JSON 文件方案的原子写、锁、迁移都是自己造的轮子，SQLite 单文件零运维且天然解决这些，当时为了最小改动选了文件存储，现在看升级点已经成熟。二是会话与行程数据会引入用户体系从第一天就做对：现在的 session_id 即身份是演示便利，后补属主校验走了兼容妥协。三是可观测性会一开始就接 OpenTelemetry：自研 span 够用但格式私有，标准化后可以接任意后端。但整体架构方向（三层微服务、降级体系、流式协议）我认为是对的，重做也不会变。
