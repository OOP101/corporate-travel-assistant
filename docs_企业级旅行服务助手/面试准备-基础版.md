> 适用：学习几个月后用这个项目面试。原则：**只说自己真正理解的内容，用简单的语言讲清楚**。
> 深度版见 `docs/面试准备.md`（如果面试官追问深了，可以参考里面的思路，但不要主动引用超出水平的词）。

## 第一部分 · 项目里用到的技术（通俗版）

### 1. Python + FastAPI（后端框架）

- **是什么**：FastAPI 是一个 Python 的 Web 框架，用来写后端接口。前端发请求过来，它负责处理并返回数据。
- **项目里干了啥**：写了三个后端服务，每个服务就是一个 FastAPI 应用，提供若干接口（比如"生成行程"、"查行程列表"）。用 `@app.post("/trips/generate")` 这样的装饰器定义接口，用 Pydantic 的 BaseModel 校验请求参数。
- **一句话解释**：我用 FastAPI 写了三个后端服务，分别负责对话编排、行程规划和实时监控，前端通过 HTTP 接口调用它们。

### 2. REST API / HTTP 基础

- **项目里干了啥**：接口遵循 REST 风格——GET 查数据、POST 创建/提交、PUT 更新、DELETE 删除。返回 JSON 格式。出了问题返回 404（不存在）、400（参数错）、403（没权限）等状态码。
- **一句话解释**：前后端之间用 HTTP 接口通信，数据格式是 JSON。

### 3. 调用大模型 API（核心）

- **是什么**：大模型（比如混元、DeepSeek）厂商提供 OpenAI 格式的 HTTP 接口，发一段对话（messages 数组）过去，它返回生成的文字。
- **项目里干了啥**：封装了一个 `LLMManager` 类统一管理模型调用。行程生成分两步：第一步发 prompt 让大模型从用户的话里提取参数（去哪、几天、几个人），第二步再发 prompt 让它按规则生成完整行程。
- **一句话解释**：后端通过 HTTP 请求调用大模型 API，把用户的需求转成结构化的行程 JSON。

### 4. Prompt（提示词）

- **项目里干了啥**：行程生成的质量靠 prompt 保证。写了一个系统提示词，里面定好规则：一天不超过 4 个景点、景点之间通勤不超过 30 分钟、按时段排餐厅、输出必须是规定格式的 JSON。
- **一句话解释**：通过写清楚的规则提示词，让大模型稳定输出我需要的 JSON 格式。

### 5. 流式输出（SSE）

- **是什么**：大模型生成内容是一个字一个字出来的，SSE（Server-Sent Events）能让后端把内容一段一段推给前端，用户就能看到文字逐渐出现，而不是等很久后一次性出现。
- **项目里干了啥**：行程生成和智能问答都做了流式输出。后端用 `StreamingResponse` 把内容分帧发出去，前端用 fetch 一段段读。
- **一句话解释**：用 SSE 做流式输出，用户几秒内就能看到内容开始出现，体验好很多。

### 6. JSON 文件存储

- **项目里干了啥**：行程、员工、政策这些数据存成 JSON 文件（一条数据一个文件），程序启动时加载到内存字典里，增删改时写回磁盘。写了一个 `BaseJsonStore` 基类，各种存储都继承它，避免重复代码。
- **一句话解释**：数据量不大，用 JSON 文件存储就够了，我封装了一个基类统一了读写逻辑。

### 7. RAG 知识库（简单版理解）

- **是什么**：RAG = 检索增强生成。先建一个知识库（比如公司差旅政策文档），用户提问时先从知识库里找出最相关的几段内容，再让大模型根据这些内容回答，这样回答有依据、不乱编。
- **项目里干了啥**：把公司差旅政策文档存起来，用户问"总监住宿标准是多少"，先搜出相关政策原文，再让大模型引用原文回答。搜索有两套：关键词匹配（简单）和向量语义检索（进阶，我把文字转成向量比相似度，代码写好了但还没接真模型）。
- **一句话解释**：做了个差旅政策知识库，大模型回答政策问题时先检索原文再回答，保证有依据。

### 8. 定时任务（APScheduler）

- **项目里干了啥**：实时监控模块用 APScheduler 每 5 分钟检查一次用户订阅的航班和天气，有异常就生成提醒。没有真实 API Key 时用模拟数据。
- **一句话解释**：用定时任务轮询航班和天气，发现异常自动生成提醒。

### 9. 降级兜底（重要设计思想）

- **项目里干了啥**：每个可能挂的环节都准备了备用方案：大模型 API 不可用就用固定模板生成示例行程；天气接口没 Key 就用模拟数据。保证演示时即使什么 Key 都没有，整个流程也能跑通。
- **一句话解释**：我给每个外部依赖都做了兜底方案，保证系统在任何情况下都能完整运行。

### 10. 前端（React + Vite）

- **项目里干了啥**：React 写了 7 个页面（智能助手、行程列表、行程详情、监控、组织、政策、审批）。用 fetch 调后端接口，用 useState 管理页面数据，流式内容收到一段就追加显示一段。组件拆成基础组件和业务组件两层复用。
- **一句话解释**：React 做了 7 个页面的工作台，数据和后端接口全部打通。

### 11. 测试（pytest）

- **项目里干了啥**：写了 60 多个测试：后端接口测试（用 FastAPI 的 TestClient 模拟请求）、存储和工具类的单元测试、完整的自动化流程验证（模拟真实使用跑一遍核心功能）。
- **一句话解释**：用 pytest 写了接口测试和单元测试，每次改完代码跑一遍，防止改坏之前的功能。

## 第二部分 · 项目介绍话术

### 30 秒版本（自我介绍时用）

> 我做了一个企业差旅助手项目，用 FastAPI 写了三个后端服务：一个负责和大模型交互的智能对话，一个负责行程的生成和管理，一个负责航班天气的实时监控。前端用 React 做了工作台页面。用户用一句话描述需求，大模型就能生成完整的多日行程，还能自动检查差旅政策、发起审批。这个项目让我把 Python Web 开发、大模型 API 调用和前后端联调完整走了一遍。

### 2 分钟版本（面试官说"介绍一下项目"时用）

> 这个项目解决的问题是：企业员工出差安排分散在聊天记录和表格里，规划费时、政策不好管控。
>
> 架构上是三个 FastAPI 后端服务加一个 React 前端。核心流程是：用户在对话框说"下周去杭州出差两天"，后端先让大模型从这句话里提取参数（目的地、日期、人数），再让大模型按我写好的规则（每天不超过 4 个景点、通勤不超过半小时、按时段排餐）生成完整的行程 JSON，用流式输出给前端，用户能看到行程逐渐出现。行程会自动保存，可以做增删改查、复用成模板。
>
> 我特别做了两点：一是降级兜底，大模型接口不可用就用模板生成示例行程，外部数据没有 Key 就用模拟数据，所以不配置任何 Key 整个系统也能完整演示；二是企业化功能，行程生成后会自动对照差旅政策检查有没有超标，需要审批的自动发起审批，主管通过后行程才生效。
>
> 开发中我踩过印象最深的坑是中文乱码：大模型返回的中文到了前端全变成乱码，排查后发现是 HTTP 响应没声明编码格式，浏览器按默认编码解析导致的，在响应头加上 UTF-8 声明后解决。这件事让我理解了 HTTP 协议里 Content-Type 和 charset 的实际作用。

## 第三部分 · 面试问答

### A. 基础题

**Q1：GET 和 POST 的区别？**

答：GET 用于获取数据，参数放在 URL 里，可以被缓存和收藏；POST 用于提交数据，参数放在请求体里。项目里查询行程列表用 GET，生成行程用 POST（因为要提交大段的需求文本）。

**Q2：常见的 HTTP 状态码？**

答：200 成功；404 资源不存在——项目里查一个不存在的行程就返回 404；400 参数错误——比如更新行程时传了不允许修改的字段；403 没权限——API Key 不对时返回 403；500 服务器内部错误。

**Q3：FastAPI 和 Flask 有什么区别？为什么选 FastAPI？**

答：两个都是 Python Web 框架。我选 FastAPI 主要因为：它自带请求参数校验（用 Pydantic 定义一个类，参数不对自动返回 400，不用手写校验）；自带接口文档（自动生成 /docs 页面，调试方便）；支持异步和流式响应（我做流式输出用到了）。Flask 更轻量，但这些都得自己装插件。

**Q4：什么是 RESTful API？**

答：一种接口设计风格：用 URL 表示资源（/trips 就是行程），用 HTTP 方法表示操作（GET 查、POST 建、PUT 改、DELETE 删），状态码表达结果。项目里的接口就是这个风格。

**Q5：Python 的列表和字典有什么区别？**

答：列表是有序的，用下标访问，适合存一组同类数据——项目里行程的天数列表就是列表；字典是键值对，用 key 访问，查找快——行程数据本身就是一个大字典（标题、目的地、每日安排都是它的值）。

**Q6：Python 的异常处理怎么用的？**

答：try/except。调用外部接口的地方我都包了 try/except——比如调用大模型 API 可能网络失败、返回格式不对，捕获后走备用方案（模板行程），而不是让整个请求崩掉。

**Q7：什么是环境变量？为什么配置放 .env 文件？**

答：环境变量是程序运行时读取的配置。API Key 这种敏感信息不能写死在代码里（上传代码库就泄漏了），放 .env 文件里，代码用 os.getenv 读取，.env 不进代码库，换环境只改配置文件不改代码。

**Q8：前端怎么和后端连接的？**

答：前端用 fetch 函数发 HTTP 请求到后端接口，带上 API Key 请求头，后端返回 JSON，前端用 useState 存起来渲染到页面。开发时 Vite 配了代理，解决跨域问题。

### B. 项目题

**Q9：介绍一下行程是怎么生成的？**

答：两步。第一步参数提取：把用户的话发给大模型，用 prompt 让它只输出 JSON，包含目的地、日期、人数、预算；第二步行程生成：把参数和我写好的规划规则（系统提示词）一起发给大模型，让它输出完整行程 JSON——每天有哪些活动、几点到几点、费用预估。拿到 JSON 后存起来，前端展示。如果解析失败会重试一次，还不行就用备用模板。

**Q10：如果大模型接口挂了怎么办？**

答：有降级方案。调用前先检查 API Key 是否配置，配置了但调用失败也会捕获异常，两种情况都走备用模板——根据用户输入猜目的地和天数，生成一份示例行程。这样保证流程不断，只是数据是演示级别的。

**Q11：流式输出是怎么实现的？**

答：后端用 FastAPI 的 StreamingResponse，把大模型返回的内容一段段包装成 SSE 格式（`data: 内容` 的文本帧）发出去；前端用 fetch 拿到字节流后一边读一边追加到页面上。用户几秒就能看到内容开始出现。错误信息单独用一个错误帧发，不和正文混在一起。

**Q12：遇到过最大的困难是什么？**

答（推荐讲乱码，真实且能体现排查过程）：
> 大模型生成的中文到页面上全变成 "æ·±å³" 这种乱码。我排查的思路是先确定乱码发生在哪一段：用 curl 直接调后端接口，发现接口返回就已经乱了，排除前端；再查后端代码，发现是 HTTP 响应没有声明字符编码，按 HTTP 老标准会默认按 ISO-8859-1 解析 UTF-8 的中文，就乱码了。在响应头加上 charset=utf-8 后解决。这个坑让我真正理解了 Content-Type 和字符编码的实际意义，也学会了分段排查定位问题。

**Q13：怎么保证改代码不改坏之前的功能？**

答：写了 60 多个 pytest 测试。接口测试用 FastAPI 自带的 TestClient，不需要真的启动服务就能模拟请求；每次改完代码跑一遍全部测试。印象最深的一次，测试帮我发现自动生成的审批单少了一个状态字段，导致审批列表里看不到它——不改的话整条审批流程实际上是断的。

**Q14：三个后端服务是怎么分工的？**

答：按职责拆的。journey-hub 是入口，接收用户对话、判断用户想干什么；planner-core 负责行程的业务逻辑（生成、增删改查、政策、审批）；sense-engine 负责定时监控航班天气。拆开的好处是各自职责清晰，监控服务出问题不影响对话。

**Q15：RAG 是什么？你的项目里怎么用的？**

答：RAG 就是先检索再回答——大模型不知道公司内部的差旅政策，直接问它会瞎编。我把政策文档存到知识库里，用户问政策问题时先搜索出最相关的几段原文，再让大模型根据原文回答，这样答案有出处。搜索目前有关键词匹配，向量语义检索的代码框架已经搭好，后续接入 embedding 模型就能支持"意思相近"的搜索而不只是关键词。

**Q16：审批功能是怎么实现的？**

答：行程生成后如果命中差旅政策（比如普通员工出差需要审批），系统自动创建一条审批单，审批人自动找该员工的主管，行程状态设为"待审批"；主管在前端审批页通过，行程状态变成"已生效"，拒绝就作废。待审批的行程不允许修改，防止绕过审批。

## 附 · 高频追问应对（基础版守防线）

| 追问 | 守防线 |
|---|---|
| "并发怎么处理？" | 目前单进程演示规模，用 Python 线程锁保护了数据写入；更大并发需要换数据库，这是我知道的升级方向 |
| "为什么不用数据库？" | 数据量小（几十条行程），JSON 文件零配置够用；我封装了统一的存储基类，换数据库只需要改一个类 |

| "部署过吗？" | 本地部署 + Docker 配置写好了；生产部署要补的是域名、HTTPS 和进程守护，这是我下一步要学的 |
| "token 是什么？" | 大模型计费和计长度的单位，约等于 0.5~1 个汉字；我的 prompt 和行程输出都控制了 max_tokens 防止超长 |
