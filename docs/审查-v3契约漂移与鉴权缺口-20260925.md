./.venv/Scripts/python.exe scripts/check_api_contract.py    # 退出码 1 = 存在死链

### 2.4 根因：三方不一致

v3 切型删掉旧三层微服务与 10 个 CRUD 路由，但：

1. **Store 层留下了** —— `department_store` / `employee_store`（有数据）在 `main.py` 的存储初始化段实例化；
2. **前端页面留下了** —— 6 个页面 + 6 条路由注册全在（`App.jsx`）；
3. **导航项留下了** —— `config/nav.js` 还把「实时监控」的副标题写成 `感知 · Sense Engine`，**广告着已删除的架构**；
4. **Vite 代理留下了** —— `vite.config.js` 里 `targets/prefixes` 仍保留 `sense` 键，注释写着"保留三个代理名兼容前端既有 fetch 调用"，等于给死链留了后门。

## 三、问题二：审批链路鉴权缺口（3 处，均有实证）

`services/core/api/approvals.py` 中：

| 接口 | 现状 | 应有 |
|---|---|---|
| `POST /approvals`（建单） | **无任何鉴权**；`employee_id` / `approver_id` 由请求体指定 | 要求登录；申请人取登录态，禁止由 body 指定 |
| `POST /approvals/{id}/approve` | **无鉴权、无角色校验**（没有 `Depends(require_admin)`） | 校验登录 + 审批人身份 |
| `POST /approvals/{id}/reject` / `cancel` | 同上 | 同上 |

实证（`.run/verify_approval_authz.py`，仅带 `X-API-Key`，**完全不带 Bearer**）：

```
POST /approvals                      (无 Bearer / 非管理员) -> 200
POST /approvals/apr_xxx/approve      (无 Bearer)            -> 200   审批=approved
```

即：**任何能访问服务的人都能给自己（或任何人）开一张审批单并当场批掉**。

另有一处闭环缺陷：手工经 `POST /approvals` 建的审批单**不会把行程置为 `pending_approval`**，
于是 `ApprovalEngine.approve()` 里的回写条件 `status == "pending_approval"` 永不成立 ——
**审批通过了，行程状态纹丝不动**（实测 `行程状态 -> None`）。

## 四、问题三：身份可伪造 → 解释历史「审批通过后列表为空」

`POST /trips/confirm` 的 `session_id`（body 参数，默认 `"default"`）会被 `deps.resolve_user_id`
直接当作行程归属（Bearer 缺席时）。实测**未登录**即可：

```
POST /trips/confirm  {"trip": {...}, "session_id": "web-user"} -> 200
GET  /trips?session_id=web-user                                -> count=1, user_id=web-user
```

**「审批通过后行程列表为空」在干净数据下不复现**：本轮的完整自动审批链路（政策命中 → 建单 →
行程置 `pending_approval` → 审批 → 回写 `planned`）一路可见，申请人视角 `count=1`。

它复现的唯一条件是**身份错位**，而真实数据里正是如此：

| 行程 | 行程 `user_id` | 审批记录 `employee_id` |
|---|---|---|
| `trip_5ac5382b13e0` | `admin` | `web-user` |
| `trip_9aa1689295df` | `demo_shooter` | `web-user` |

审批单上申请人写着 `web-user`，行程却归档在 `admin` / `demo_shooter` 名下 —— 申请人登录后按
`list_by_user(自己)` 取数自然是空。**这不是后端过滤 bug，是身份可伪造导致的数据错位。**
