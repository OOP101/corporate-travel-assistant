# PRD · 行程规划对话流程（v2 重写）

> 版本：v2（2026-09-03 重写）｜ 适用：ChatPage 对话入口 + TripsPage 规划入口 ｜ 状态：待评审 → 按本 PRD 改造 planner-core / journey-hub / 前端  
> v1 问题复盘触发：用户实测「我下周要去深圳」→ 系统生成"深圳3天文化自然人文之旅"，与预期（出差）完全不符，天数/酒店/活动均为系统臆造。



---

## 1. 背景：v1 流程为什么是坏的（实测证据）

### 1.1 一次真实会话（2026-09-03，hy-mt2-pro，实测复现）

用户输入（完整原文）：

> 我下周要去深圳

系统产出：

```
🧳 行程已生成
标题：深圳3天文化自然人文之旅
目的地：深圳
天数：3 天
· 2026-09-07 / 历史人文探索之旅（5 项活动）
· 2026-09-08 / 自然风光观赏之旅（5 项活动）
· 2026-09-09 / 文化休闲收尾之旅（4 项活动）
出行清单：4 项
✅ 政策检查通过 ｜ 🖊️ 已自动发起审批（审批人：李明远）
```

用户反馈：**「我不是去旅游啊，我只是说我要去。中间去多少天、在那里待着、酒店的选择，这都是随机的吗？」**

### 1.2 根因（对照代码，非猜测）

| #  | 缺陷                      | 代码证据                                                                                                                                                                 | 后果                                                                 |
| -- | ----------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------ |
| D1 | 参数提取用「带默认值的示例 JSON」诱导模型 | `planner-core/generators/itinerary.py` L249-269：模板示例 `"days": 3`、`"budget_total": 5000`、`"travel_style": "…cultural (未提及则 cultural)"`、`"interests": ["自然风光","历史人文"]` | LLM「抄作业」：用户没说的天数=3、风格=cultural、兴趣=自然/人文全被抄进参数 → 标题「3天文化自然人文之旅」逐字对应 |
| D2 | 代码层兜底默认值继续固化臆造          | 同文件 L313-324：`setdefault("days",3)`、`budget_total=5000`、`travel_style="cultural"`                                                                                    | 提取缺失也不报「缺参」，静默补默认                                                  |
| D3 | 生成引擎是「通用旅游引擎」，无企业差旅约束   | 同文件 `PLANNING_RULES` L36-91：只约束景点数量/门票/亲子/老人节奏，通篇无「出差/会议/客户拜访/报销合规」                                                                                                  | 只要用户没说「出差/开会」，模型一律按景点游方向编                                          |
| D4 | 对话流程缺少「澄清」环节            | 无任何缺参反问逻辑；提取失败/缺参 → 直接带默认值生成                                                                                                                                         | 信息不足也硬造，用户对结果零控制                                                   |
| D5 | 前端把一切压成一句话              | `TripsPage.jsx` 生成表单仅 `query` 一个字段（L236-239）；ChatPage 同理                                                                                                             | 没有「场景/天数/目的」的结构化选择入口，全部甩给 LLM 猜                                    |
| D6 | 产品宣言与实现脱节               | `README.md` 宣称「商务出差/客户拜访/会议参展/团队出行多场景自适应」；实现无场景概念                                                                                                                    | 文档写的场景自适应根本不存在                                                     |

### 1.3 结论

v1 = 「单条自然语言 → 旅游引擎 → 直接落库并自动审批」。**用户信息缺口、场景类型、酒店等关键决策全部缺失，被静默代填且不可见**。审批对象（李明远）在行程内容都是错误的前提下被自动触发，放大错误。

## 2. 目标与非目标

### 2.1 目标

1. 行程需求的第一步是**明确场景**（差旅/会议/客户拜访/团队出行/个人出行…），场景由用户选择，系统不得擅自假设。
2. 关键参数缺失时**反问澄清**，且澄清有界（见 §6）；仅次要字段允许代填，且**代填值必须显式展示给用户确认**。
3. 生成内容（天数/日期/住宿/活动）**全部来源于用户确认过的参数**，系统不臆造任何一项。
4. 生成完成后先给「方案确认页」，用户确认才落库/触发审批。
5. 支持「补充/修改参数 → 重新生成」，酒店等单项可单独调整。

### 2.2 非目标（本版不做）

- 不做预订/支付闭环（仅行程方案层）。
- 不做多行程并行管理（单会话内一次推进一个方案）。
- 不做同用户跨会话行程记忆复用（后续可做「常用线路模板」）。

## 3. 角色与场景模型

### 3.1 场景（scene）—— 由用户选择，必选项

| scene      | 名称    | 典型构成           | 生成偏好                            |
| ---------- | ----- | -------------- | ------------------------------- |
| `business` | 商务出差  | 会议 / 拜访 / 现场办公 | 以 meeting/visit 为主；酒店按差旅标准；不含景点 |
| `meeting`  | 会议/参展 | 参会/布展/撤展       | 围绕会程时间表排期；留布撤展缓冲                |
| `visit`    | 客户拜访  | 约见客户/商务宴请      | 按客户约见时间排期；预留通勤缓冲                |
| `team`     | 团队出行  | 团建/培训/多部门      | 统一集合节奏；含集体活动与住宿分配               |
| `personal` | 个人出游  | 游玩/探亲          | 景点/休闲节奏（即 v1 旅游引擎可复用部分）         |

> 决策记录：v1 未定义场景，模型自由发挥导致差旅需求被生成成旅游行程。**场景由用户主动选择或系统反问确认**，任何路径都不得静默假设。

### 3.2 触发场景选择的两种入口

- **入口 A（表单）**：TripsPage/对话输入框提供场景下拉（默认空，提示「选择出行场景」）；选完再填需求，需求框 placeholder 按场景变化（例：business → "例：9月15号广州飞北京，16号上午拜访国贸客户…"）。
- **入口 B（对话）**：用户只说「我要去深圳」时，助手反问一句完成场景 + 关键信息（§6.2 澄清话术），用户点选项或回一句即可。

## 4. 行程参数模型（v2）

> 字段来源对齐 v1 extract（destination/origin/start_date/days/人数/预算/风格/饮食/兴趣/备注），新增 `scene` 与差旅字段；剔除诱导默认值。

| 参数                      | 必填性                 | 来源        | 说明                               |
| ----------------------- | ------------------- | --------- | -------------------------------- |
| `scene`                 | **必填**              | 用户选择/反问确认 | §3.1                             |
| `destination`           | 必填                  | 用户        | 无目的地则无法生成                        |
| `start_date`            | 必填                  | 用户        | 相对日期（下周一）由系统换算并**回显确认**          |
| `end_date` / `days`     | 必填（二选一）             | 用户        | 用户说「3 天」与说「9/7-9/9」等价；都未说 → 反问   |
| `origin`                | 选填（可代填）             | 用户/当前城市   | 代填需在确认页展示                        |
| `num_*`（人数构成）           | 选填（可代填 1 成人）        | 用户        | 默认 1 人出差，展示确认                    |
| `purpose`（出差事由/拜访对象）    | business/visit 类建议填 | 用户        | 供生成工作日程与审批说明                     |
| `budget_total`          | 选填（可代填=按差旅标准）       | 用户/政策标准   | 企业用户可自动取该员工政策标准，需展示来源            |
| `hotel`（等级/位置偏好）        | 选填                  | 用户        | 不选 → 按差旅政策标准生成 1 家建议住宿，**确认页可换** |
| `dietary` / `interests` | 选填                  | 用户        | 无默认示例诱导；空则不写兴趣                   |
| `notes`                 | 选填                  | 用户        | 备注透传                             |

### 4.1 「必填 vs 可代填」判定规则

1. 缺 `scene` / `destination` / `start_date` / `days(end_date)` → **必须澄清**，不得生成。
2. 缺 `origin` / 人数 / `budget` / `hotel` → 允许代填，但：
   - 代填值必须有**明确规则**（如 origin=常驻地、budget=员工政策标准、hotel=按政策上限）而非模型自由发挥；
   - 代填值**必须在确认页列出**（格式：`[代填] 出发地=西安（你的常驻地）`），用户可改后重生成。
3. 除上表外任何字段，模型不得自行发明新维度。

## 5. 对话流程状态机（核心）

```
        ┌────────────────────────────────────────────────────┐
        ▼                                                    │
  [S0] 开始（用户描述需求 / 点示例）                            │
        │                                                    │
        ▼                                                    │
  [S1] 需求解析（场景识别 + 参数抽取）                           │
        │  —— 用户已选场景/信息齐 → S3                         │
        │  —— 场景或必填缺失 → S2                             │
        ▼                                                    │
  [S2] 澄清回合（反问，≤2 轮，见 §6）                           │
        │  用户补齐 → S3                                      │
        │  用户说「你看着办/随便」→ 授权代填 → S3（标注代填）     │
        │  2 轮仍缺 → 停止并给「手动创建行程」引导              │
        ▼                                                    │
  [S3] 生成行程方案（流式进度/摘要，酒店=1 家建议+备选）          │
        │                                                    │
        ▼                                                    │
  [S4] 方案确认（关键！新增环节）                              │
        │  —— 展示：场景徽标 / 日期天数 / 目的地 / 人数 /        │
        │     预算（含 [代填] 标注）/ 酒店建议 / 每日骨架        │
        │  —— 操作：确认生成｜改参数重排｜换酒店｜取消            │
        ▼                                                    │
  [S5] 确认 → 落库 + 政策检查 + 审批流（v1 已有）                │
        ▼                                                    │
  [S6] 完成：气泡展示卡片 + 「调整行程/订阅监控/去报销」等入口
```

**关键变更 vs v1**：

- 新增 **S2 澄清回合** 与 **S4 方案确认** 两个节点；v1 是从 S1 直接跳 S3 再自动落库审批。
- **自动审批只允许在 S5（用户确认后）发生**；S4 之前绝不触发审批。修正 v1「内容错误仍自动审批给李明远」的问题。

## 6. 澄清回合规范（S2）

### 6.1 澄清顺序（一次最多问 3 项，按优先级）

1. 场景（若完全无法判定且用户未选）
2. 日期与天数（合为一项问）
3. 目的/事由（business/visit 时）

> 缺 4 项以上时：问「是否按常见差旅默认补全？」给一键授权，避免审问式体验。

### 6.2 话术模板（统一风格，前端做成可点选项）

- 场景：`请问这次去{目的地}是？` → 选项：商务出差 / 会议参展 / 客户拜访 / 团队出行 / 个人出游
- 日期：`计划哪几天去？可以说「下周一」「周五出发」或具体日期。`
- 天数：`大概待几天？`
- 事由：`这次出差的主要事项是？`（会议 / 拜访客户 / 现场办公…）
- 兜底授权：`如果没有特别要求，我按「{9/7-9/8} 商务出差 2 天、住宿按贵司标准」出一版方案，可以吗？`

### 6.3 澄清上限

- 同一行程最多 2 轮反问；第 3 轮仍未补齐 → 明确告知缺哪几项并引导「去 TripsPage 手动填写」。
- 追问不得打断上一条回答的展示；用户可随时说「随便/你看着办」跳过（= 对代填的显式授权）。

## 7. 生成内容规范

| 项目    | 规范                                                                                                    |
| ----- | ----------------------------------------------------------------------------------------------------- |
| 天数/日期 | 只准来自确认过的参数；出现「已生成 3 天」等文案时括号回显来源参数                                                                    |
| 场景内容  | 按 §3.1 偏好；business/meeting/visit **禁止生成景点类活动**；personal 才允许                                           |
| 酒店    | 数据源=腾讯地图 POI（`hotel_options`，已接入，真实数据）：1 家主选 + ≤2 家备选，字段含名称/区域/地址/坐标；**参考价标注「以预订平台为准」（腾讯 POI 不返回房价，不做硬比对）**；business 类住宿位置默认取会场/客户地附近（POI nearby 搜索）；「换一家」直接切换 `hotel_options` 选中项，无需重新生成 |
| 预算    | 企业用户有政策标准时，未填预算 = 引用政策标准并标注；费用项逐项可归因（用于报销）                                                            |
| 审批    | 只在 S5 确认后发起；审批说明附 scene/purpose                                                                       |

## 8. 确认页（S4）交互要求

TripsPage 与 ChatPage 共用同一「方案确认卡片」组件：

- 顶部：`[场景徽标] 标题 · {起始日期}~{结束} · {目的地} · {n}人`
- 参数区逐行列出，代填项带 `[代填]` 前缀 + 来源说明 + 可编辑
- 每日骨架（只读预览：上午/下午/晚间 3 行摘要 + 活动数）
- 酒店建议区：主选卡片 + 「换一家」下拉备选（数据源=`hotel_options` 真实 POI，换选不重排行程）
- 底部操作：`确认并提交审批`（primary）｜ `改参数重新生成`（secondary）｜ `取消`
- 提交前若检测到政策违例项，用警示条列出（如超住宿标准），用户可「仍然提交」或返回修改

## 9. 与现有系统对齐（改造落点）

| 层                                      | 改动                                                                                                                                                                                         |
| -------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| planner-core `generators/itinerary.py` | ① extract prompt 删除所有示例默认值，字段标注「未提及=空」；② 新增 `scene` 抽取与缺失清单输出；③ `PLANNING_RULES` 拆分 scene 规则（business 时段以 meeting/visit 为主、禁景点；personal 保留旅游节奏）；④ 兜底逻辑只补可代填字段并记录 `defaulted[]`，必填缺失时抛出缺参结果 |
| planner-core API                       | 生成接口支持返回「缺参清单 / 方案草案（未落库）/ 已确认」三态；`/trips/generate` 前先过缺参校验                                                                                                                                |
| journey-hub `handlers.py / graph.py`   | plan 意图按四态流转：`clarify`（S2 反问帧，附选项）→ `generate`（S3 草案）→ `confirm`（S4 确认帧，前端卡片）→ `done`（S5 落库+审批）。新增事件帧 `clarify`、`confirm`、`assumptions`（代填项）                                               |
| 前端 `ChatPage.jsx / TripsPage.jsx`      | 场景下拉/对话场景选项；澄清选项 chips；方案确认卡片组件（§8）；「你看着办」授权入口                                                                                                                                             |
| 审批触发                                   | journey 审批调用从「plan 完成即触发」改为「收到用户 confirm 才触发」                                                                                                                                              |

**分期**：P1 = 必填校验 + 澄清回合（S1/S2）+ 场景选择；P2 = 方案确认页（S4）+ 酒店可换 + 代填标注；P3 = 场景化生成规则完整落地（PLANNING_RULES 按 scene 拆分）。
